PROFESSIONAL CASE STUDY / POC

ILAC — IFSF LON API Converter

A compatibility bridge between the OpenRetailing Price Pole API Collections and installed IFSF LON Price Pole equipment.

PUBLICATIONS IN RESUMEHAIA WORK
01 / PROBLEM

Modern API clients, installed legacy OT

Forecourt environments can contain installed Price Pole equipment built around IFSF LON while newer systems expose REST-based OpenRetailing Price Pole APIs. The engineering problem is translating between endpoint-oriented API resources and the IFSF database/message model without forcing immediate field replacement.

02 / CONSTRAINTS

C++11 · legacy drivers · 32-bit Windows · binary protocol structures

The system must preserve compatibility with established field hardware and legacy development constraints while handling acknowledgements, responses, binary data formats, simulator validation, and portability work.

03 / MY OWNERSHIP

Lead developer, architect, and primary technical decision-maker

ILAC began as my Haia internship project and continued after the internship. A second developer joined in 2026 under my supervision. I now lead the two-person team, designed the architecture, remain the main developer, and make the primary technical decisions across the REST/Oat++ boundary, IFSF message handling, conversion logic, concurrency, response processing, and validation.

04 / ENGINEERING DECISIONS

Preserve OT behind a modern API boundary

ILAC isolates conversion responsibility rather than requiring installed equipment to be replaced. The architecture preserves the existing C++11/legacy environment while exposing a modern REST-facing boundary.

05 / ARCHITECTURE

OpenRetailing Price Pole APIs → REST/HTTP → ILAC → IFSF messages → LonTalk / TP/FT-10 → Price Pole

Oat++ exposes the HTTP boundary; ILAC maps API resources to IFSF Database Address (DB_Ad) + Data Identifier (Data_Id) operations, sends the corresponding application messages over LonTalk / TP/FT-10, and converts responses back into API data.

06 / STANDARDS BASIS

Price Pole APIs mapped to IFSF database and message semantics

Engineering Bulletin No. 27 documents the same conversion domain: OpenRetailing Price Pole API Collections v1.0 mapped to IFSF Part 3-02 Price Pole Application v1.24 and Part 2-01 Communications over LonWorks v1.93. In that model, REST GET operations typically map to Read → Answer and REST POST/update operations to Write → Acknowledge. IFSF data is addressed using DB_Ad + Data_Id, while Engineering Bulletin No. 11 defines common encodings such as UNIT_PRICE = bin8 + bcd6.

Working Group proof-of-concept demonstration

The proof of concept demonstrated a practical modernization path between modern APIs and installed legacy OT. IFSF Engineering Bulletin No. 27 documents the same standards-conversion domain and was solely authored by Nicholas Le Roux.
